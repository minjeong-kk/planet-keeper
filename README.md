# planet-keeper

An educational climate game to reach planetary equilibrium through environmental control and science quizzes.

---

# 데이터 수집 스크립트 설치

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

# 데이터 파이프라인

실측 데이터를 수집해 물리 엔진의 판정 임계값을 도출합니다.

```bash
# 1. 실측 수집 (API 키 필요, .env 참고)
cd data-pipeline/Scripts
python3 observed-gk2a.py       # 천리안 산출물 + 좌표 앵커 → observed_gk2a_dataset.csv
python3 observed-kim.py        # 같은 좌표의 KIM t2m/psl → observed_kim_dataset.csv
python3 physics-kim.py         # KIM 전지구 필드 평균 → physics_kim_dataset.csv
python3 physics-gk2a.py        # 천리안 SWRAD 평균 → physics_gk2a_dataset.csv
python3 physics-merge.py       # 위 결과 + CO2 병합 → physics_reference.csv

# 2. 지점 선택용 실측 수집 (행성 만들기의 "특정 지점 선택")
python3 probe-kim-vars.py      # 필요한 KIM 변수가 살아 있는지 확인 (선행)
python3 preset-kim.py          # 5지점 × 변수 4종 → preset_kim_cache.csv

# 3. 도출·변환
cd ../Analysis
python3 derive_thresholds.py   # 실측 t2m 분포 → climate_thresholds.json
                               #                + src/data/climateThresholds.js
python3 build_presets.py       # preset_kim_cache.csv → src/data/climatePoints.js
```

> `derive_thresholds.py`와 `build_presets.py`가 각 출력 파일의 **유일한 생성자**입니다.
> 값이 어긋날 수 없는 구조이므로 별도의 동기화 검사가 필요 없습니다.
> `preset-kim.py`는 한 건씩 캐시에 flush하므로 중간에 끊겨도 다시 실행하면 이어받습니다.

## 실측 데이터가 쓰이는 경로

```
observed_kim_dataset.csv (KIM t2m, 1,498지점)
        │
        └─ derive_thresholds.py ─→ COLD_STABLE_MAX_K / EARTH_LIKE_MAX_K
                                            │
                                            └─→ physicsEngine.planetStateOf()
                                                 (게임의 5분류 판정)

preset_kim_cache.csv (KIM 5지점, t2m·tcld·dswrsfc·rss·ps)
        │
        └─ build_presets.py ─→ climatePoints.js
                                    │
                                    ├─ values  → 슬라이더 초기값
                                    ├─ t2m     → 시작 온도
                                    └─ surfaceAlbedo → albedoOf()의 지표면 반사율
```

# 파일별 역할

| 파일 | 역할 |
|------|------|
| **Scripts/observed-gk2a.py** | 천리안(GK2A) 산출물을 받고, 정지궤도 투영으로 위경도를 계산해 표본 좌표를 만듦. |
| **Scripts/observed-kim.py** | 위 좌표와 같은 지점·시각의 KIM 수치모델 `t2m`/`psl`을 조회해 1:1 매칭. |
| **Scripts/physics-kim.py** | KIM 전지구 필드 평균(복사 5변수)을 월별로 수집. |
| **Scripts/physics-gk2a.py** | 천리안 SWRAD(지면 흡수단파) 전지구 평균을 월별로 수집. |
| **Scripts/physics-merge.py** | 위 둘과 CO₂ 실측을 합쳐 `physics_reference.csv` 생성. |
| **Scripts/probe-kim-vars.py** | KIM에 필요한 변수(`t2m`/`tcld`/`dswrsfc`/`rss`/`ps`)가 있는지 확인. API가 변수 목록을 주지 않아 이름을 찾아낸 결과를 기록해 둠. |
| **Scripts/preset-kim.py** | 지점 선택용 실측 수집. 기온·구름은 조회 구간 전체에 12일 분산, 단파복사는 남극에 태양이 남은 2~3월로 고정(한계 9번 ①). |
| **Analysis/config.py** | 데이터 파이프라인 공용 경로 상수. |
| **Analysis/derive_thresholds.py** | 실측 t2m 분포에서 판정 임계값을 도출해 `climate_thresholds.json`(기록용)과 `src/data/climateThresholds.js`(프론트가 import)에 저장. |
| **Analysis/build_presets.py** | 수집 결과를 `src/data/climatePoints.js`로 변환. 물리 단위 → 슬라이더 변환을 여기 한 곳에만 둔다. |

> `Scripts/`는 API 수집(네트워크·인증 키 필요), `Analysis/`는 수집된 파일만으로 하는
> 오프라인 도출입니다. 스크립트 이름과 출력 파일 이름이 짝을 이룹니다
> (`observed-kim.py` → `observed_kim_dataset.csv`).

# 알려진 한계 (Known Limitations)

## 1. Physics Engine 기준값의 한계

- `physics_reference.csv`는 2026년 1~7월에서 **달마다 하루씩 뽑은 7일**의 평균입니다
  (연속 7일이 아니라, 특정 주에 편향되지 않도록 월별로 분산시킨 표본입니다).
- 전 지구 연평균이 아니라 해당 기간의 대표값입니다.
- 따라서 절대적인 지구 기준값이 아닌, 물리 엔진 계산을 위한 기준값으로 사용합니다.

### 기준 상수: 계획서 값과 실측값 대조

물리 엔진의 기준 상수를 개발계획서 값과 실측값 양쪽으로 산출해 대조한 결과입니다.
**관측으로 정할 수 있는 값은 실측으로 교체했고, 실측 쪽에 해결되지 않은 편향이 있는
항목은 계획서 값을 유지하되 그 사유를 남깁니다.**

| 상수 | 계획서 | 실측 | 채택 | 근거 |
|---|---|---|---|---|
| `SOLAR_CONSTANT` | 100 | **297.88** W/m² | ✅ 실측 | KIM `dswrtoa` 전지구 필드 평균 |
| `CO2_BASELINE_PPM` | 432 | **429.53** ppm | ✅ 실측 | 기상청 3개소 2024년 월별 36개 평균 |
| `COLD_STABLE_MAX_K` | — | **281.61** K | ✅ 실측 | 관측 t2m 1,498지점 IQR |
| `EARTH_LIKE_MAX_K` | — | **294.69** K | ✅ 실측 | 〃 |
| `REFERENCE_TEMP_K` | 288.15 K | (291.55 K) | ⬜ 계획서 | 아래 ① |
| `ENERGY_BALANCE_EPSILON` | 5.0 | — | ⬜ 설계값 | 아래 ② |
| 온실효과 기준 `g` | 0.30 (출처 없음) | **0.386** | ✅ 실측 | 실제 지구 OLR 240 W/m² |
| 지표별 알베도 | (해당 항 없음) | **0.8 / 0.08 / 0.2** | ✅ 문헌값 | 아래 ③ |
| 구름 알베도 | 0.5 | — | ⬜ 계획서 | 계획서 (3)1, 그대로 유지 |

**① `REFERENCE_TEMP_K` — 실측 평균을 쓰면 안 되는 값입니다.**
관측 t2m 평균은 291.55 K로 지구 평균보다 따뜻하게 치우쳐 있습니다(여름철·저위도 표본
편중, 한계 2번). 그래서 관측에서는 **분포의 폭(IQR)만** 가져와 위 두 임계값을 만들고,
중심은 계획서의 "현대 지구 평균 15°C = 288.15 K"에 고정합니다. 물리 엔진도 같은 값을
`climateThresholds.js`에서 가져다 써서 **평형 보정 목표와 판정 밴드 중심이 항상 일치**합니다.

**② `ENERGY_BALANCE_EPSILON` — 관측량이 아니라 설계 허용오차입니다.**
`|ΔE| ≤ epsilon` 이면 평형으로 봅니다. 5.0은 S=100 스케일에서 "평형온도로부터 약
4.6 K 이내"에 해당하던 값이고, S를 실측값으로 바꾸면서 같은 온도 폭을 유지하도록
`5.0 × (SOLAR_CONSTANT / 100)` 으로 유도합니다(현재 **14.894**). 숫자를 따로 적지 않고
`SOLAR_CONSTANT`에서 유도하는 이유는, 한쪽만 고치면 에러 없이 판정 기준선만 조용히
어긋나기 때문입니다.

**③ 지표별 알베도 — 문헌값을 계수로 직접 씁니다.**

예전 공식은 `a = 0.12 + 0.45·빙하 + 0.5·구름 − 0.05·바다` 였습니다. 계획서에서 온 값은
구름 계수 `0.5` 하나뿐이었고 나머지 세 계수는 출처가 없었는데, 극단 조성에서 실제와
크게 어긋났습니다.

| 조성 | 예전 공식 | 현재 | 실제 |
|---|---|---|---|
| 바다 100% | 0.22 | **0.08** | 해양 0.06~0.10 |
| 육지 100% (사막 행성) | 0.145 | **0.20** | 육지 0.15~0.35 |
| 구름 100% | 0.62 | **0.50** | 구름 ≈0.5 |
| 기준 조성 | 0.28 | **0.27** | 지구 ≈0.30 |

원인은 구름을 **지표에 더하는 항**으로 둔 것이었습니다. 구름은 지표를 가리므로 면적
가중으로 결합해야 하고, 그렇게 하면 구름 100%에서 지표가 무엇이든 구름 알베도 0.5가
나옵니다. **계획서의 `0.5`는 버리지 않고 "구름 자체의 반사율"로 그대로 씁니다.**

```
육지   = max(0, 1 − 빙하 − 바다)
지표면 = (빙하·0.8 + 바다·0.08 + 육지·0.2) ÷ (빙하 + 바다 + 육지)
a      = 지표면 × (1 − 구름) + 구름 × 0.5
```

계수는 전부 문헌 통념값입니다 — 눈·얼음 0.8(신적설 0.8~0.9, 스노우볼 지구 추정 0.6~0.8),
해양 0.08(0.06~0.10), 육지 0.2(숲 0.15 ~ 사막 0.35).

> 물리 엔진은 기준 조성이 288.15 K에서 에너지 평형이 되도록 유효 σ를 자동 보정하므로,
> 알베도 절대값이 바뀌어도 평형 기준점(288.15 K)은 유지됩니다.

**공식 교체의 대가:** 행성 알베도가 가장 밝은 지표(눈·얼음 0.8)를 넘을 수 없게 되어
도달 범위가 `0.07~0.90`에서 `0.08~0.80`으로 좁아졌습니다. 물리적으로는 옳지만 플레이어의
냉각 수단이 줄어듭니다. 온실효과 상한을 0.8에서 0.85로 완화해(금성이 `g ≈ 0.99`) 일부를
회복했습니다 — 예전 상한에서는 무작위 조성의 27%가 벽에 붙어 CO₂·대기두께 아이템이
화면상 아무 효과가 없었고, 지금은 21%입니다.

무작위 행성 400개를 아이템으로 공략한 결과입니다.

| 선택 방식 | 평형 도달 | 필요 아이템(중앙값) | 상위 10% |
|---|---|---|---|
| 매번 최선의 아이템 | 81.8% | 2개 | 4개 |
| 후보 4개 중 무작위 (실제 플레이에 가까움) | **88.3%** | **7개** | **25개** |

최선 선택이 오히려 성공률이 낮은 것은 강한 아이템이 평형을 지나쳐 버리기 때문입니다.
**성공률보다는 필요 아이템 수(= 풀어야 하는 문제 수)가 실질적인 난이도**이며, 상위 10%
구간의 25개는 조정 대상입니다.

### 계획서 선형식 → 로그·σT⁴ 전환

계획서의 두 식을 물리 표준형으로 바꿨습니다. 둘 다 **선형 근사를 비선형 원식으로**
되돌린 것입니다.

**① 평형온도: 선형식 → 슈테판–볼츠만 역산**

```
계획서   T = 15 + ((Total_Energy − 142) × 0.5)
현재     T_eq = T_current × (ASR / OLR)^¼        ← ASR = OLR 을 T에 대해 푼 것
```

계획서 식은 "에너지 1 W/m²당 0.5℃"라는 고정 기울기를 전제합니다. 이는 계획서 고유의
에너지 분배 모델에서 나온 계수라, `OLR = ε·σ·T⁴` 를 쓰는 이 엔진에 그대로 옮기면 단위가
맞지 않습니다. 그래서 같은 목적(평형온도 산출)을 **엔진 자신의 방정식을 역산**하는
방식으로 구현했습니다. 닫힌 형태라 반복 계산도 필요 없습니다.

**② CO₂ 응답: 선형 → 로그**

```
현재     co2Term = 0.25 × log₂(CO₂ / 429.53ppm)
```

CO₂ 복사강제력이 농도의 로그에 비례한다는 것은 기후물리의 표준 결과입니다
(`ΔF ≈ 5.35 · ln(C/C₀)`). 농도가 2배가 될 때마다 같은 폭으로 효과가 커지므로, 게임에서
CO₂를 계속 올려도 효과가 무한히 커지지 않고 완만해집니다. 선형으로 두면 저농도에서
과대평가되고 고농도에서 발산합니다.

### 스케일 불변성

`SOLAR_CONSTANT`를 100에서 297.88로 바꿔도 **게임 판정은 달라지지 않습니다.**
`EFFECTIVE_SIGMA`가 S에 비례해 함께 보정되므로 평형온도가 불변이고, ΔE만 2.9788배로
커지기 때문입니다. ΔE 단위를 가진 임계값들을 같은 배율로 환산하면 판정이 그대로
유지되며, 실제로 슬라이더 조합 4,000개 × 평형온도 기준 오프셋 9종 = **36,000개 표본에서
라벨·평형온도·한 틱 뒤 온도·ΔE/epsilon 비율이 전부 일치**함을 확인했습니다(최대 오차 0).

화면에 표시되는 ΔE 숫자만 3배 커지므로, 플레이어가 그 값을 판단할 수 있도록
게임 화면과 리포트에 평형 판정 기준선(±14.9 W/m²)을 함께 노출합니다.

## 2. 실측 데이터의 한계

- `observed_kim_dataset.csv`는 KMA API 조회 기간(최대 약 180일)의 제약을 받습니다.
- 모든 계절을 포함하지 못하며, 특정 기간의 실제 기상 특성을 반영합니다.
- 표본 좌표가 천리안 관측 영역(동아시아·서태평양) 안에 있어 여름철·저위도로 치우쳐
  있습니다. 그래서 `derive_thresholds.py`는 관측 **평균**을 쓰지 않고 **분포의 폭(IQR)**
  만 가져오며, 중심은 계획서 기준값 288.15 K에 고정합니다.

---

## 3. CO₂ 데이터 시차

- CO₂는 기후변화감시소의 실측 자료를 사용합니다.
- KIM/GK2A 데이터보다 약 1~2년 이전 자료를 사용하지만, CO₂는 단기간 변화가 비교적 작아 근사값으로 활용합니다.

---

## 4. 이상 기후 상태

- 온실폭주(Runaway Greenhouse), 스노우볼(Snowball), 극한 고온·저온 등 실제 관측이 어려운 기후 상태는 물리 엔진이 직접 계산합니다.
- 따라서 해당 상태의 품질은 물리 엔진 모델(0차원 에너지 수지)의 타당성에 의존합니다.

---

## 5. 위성 데이터 격자 매칭

- GK2A 산출물(SAL, TPW, CLA 등)은 서로 다른 공간 해상도를 가지므로, 최근접 이웃(Nearest Neighbor) 방식으로 동일 위치를 매칭합니다.
- 이 과정에서 작은 공간 오차가 발생할 수 있습니다.

---

## 6. 복사량 전지구 평균의 편향

수집한 복사량 평균은 두 소스 모두 이론값에서 벗어나 있으며, **방향이 서로 반대**입니다.

| 값 | 실측 | 이론/통념 | 편차 |
|---|---|---|---|
| GK2A `SWRAD` (지면 흡수단파) | 333.85 W/m² | ≈240 W/m² | **+39%** |
| KIM `dswrtoa` (TOA 하향단파) | 297.88 W/m² | 340.3 W/m² | **−12.5%** |

- **GK2A 쪽**은 원인이 설명됩니다 — 여름철·동아시아 영역 중심의 자료이고, 정지궤도
  영상의 픽셀을 동일 가중치로 평균해서 실제 면적보다 저위도(태양복사가 강한 지역)의
  영향이 크게 반영됩니다.
- **KIM 쪽(−12.5%)은 원인을 특정하지 못했습니다.** 격자 가중 방식일 수도, 필드 평균의
  적용 범위일 수도 있습니다. 이 편향 때문에 KIM 필드 평균에서 유도한 알베도·온실효과
  비율을 채택하지 않았습니다(한계 1번 ③).

`SWRAD`는 분류 모델을 제거하면서 물리 엔진 계산 경로에서 빠졌고, 지금은
`physics_reference.csv`에 기록만 남아 있습니다. `dswrtoa`는 `SOLAR_CONSTANT`로 쓰이지만,
이 상수는 스케일 기준이라 절대값의 편향이 게임 판정에 영향을 주지 않습니다
(한계 1번 "스케일 불변성" 참고).

## 7. 분류 모델(ML)을 제거한 이유

계획서 (2)①은 ML 분류기를 명시했고, 실제로 구현해 **정확도 0.9694**까지 확보했습니다.
그러나 성능을 측정하는 과정에서 **라벨이 입력 피처만으로 완전히 결정된다**는 사실이
드러나 최종적으로 제거했습니다.

피처 5개를 조합하면 알베도가 그대로 복원되고,

```
albedo = min(0.9, surface_albedo + 0.5 × cloud)
ΔE     = S(1 − albedo) − (1 − greenhouse) · σ · T⁴
```

라벨을 정하는 `ΔE`까지 계산됩니다. 즉 모델은 **게임이 이미 정확히 계산할 수 있는
함수를 근사**하고 있었고, 물리 엔진 규칙과의 일치율은 0.9720이었습니다.
**나머지 2.8%는 모델이 틀린 것입니다.**

지금은 `src/utils/physicsEngine.js`의 `planetStateOf()`가 같은 판정을 정확값으로
수행합니다.

| | 제거 전 (ONNX) | 제거 후 (물리 엔진) |
|---|---|---|
| 물리 규칙 일치율 | 0.9720 | **1.0000** |
| 번들 크기 | wasm 13 MB + 모델 7 KB | **0** |
| 판정 방식 | 비동기 (모델 로드 후 추론) | **동기, 즉시** |
| 학습 파이프라인 | 스크립트 8개 + 합성 52,056행 | **불필요** |

### 제거 전까지의 모델 탐색 기록

계획서가 명시한 RandomForest가 이 문제에 맞지 않는다는 것도 이 과정에서 확인했습니다.
라벨 경계가 `σ·T⁴`와 `log₂(CO₂)`가 섞인 **매끄러운 곡면**인데, RandomForest는 축에
평행한 계단으로만 자릅니다. 신경망은 연속 함수라 가중치 1,413개로 같은 경계를
표현했습니다.

| 모델 (피처 5개) | 정확도 | ONNX | 불평형 오판율 |
|---|---|---|---|
| RandomForest(10, 깊이8) | 0.7513 | 272.6 KB | 54.6% |
| RandomForest(30, 깊이12) | 0.8236 | 6,079.8 KB | 39.9% |
| GradientBoosting(100) | 0.7966 | 276.7 KB | 47.0% |
| MLP(32, 32) | 0.9694 | 7.0 KB | 5.0% |

모델 계열을 바꿔가며 정확도를 0.75 → 0.97까지 끌어올린 뒤에야, **애초에 근사할
필요가 없는 문제**였다는 결론에 도달했습니다.

### 실측 데이터는 그대로 쓰입니다

ML을 걷어내도 실측 데이터의 소비 경로는 유지됩니다. 학습에 쓰이던 52,056행은
**물리 엔진이 만든 합성 데이터**였고, 실측 `t2m` 1,498지점은 지금도 게임의 판정
임계값을 결정합니다(위 "실측 데이터가 쓰이는 경로" 참고).

## 8. 계획서와 달라진 점

### ML 분류기 제거 (7장)

계획서 (2)①의 ML 분류기를 구현했다가 제거했습니다. 창의성 항목의
*"ML 분류 결과가 게임 판정(클리어 조건)에 직접 반영"* 도 함께 해당됩니다.

판정은 물리 엔진(`planetStateOf`)이 담당합니다 — 100% 정확하고 즉시 계산되며,
ML은 그 규칙의 근사일 뿐이었기 때문입니다. 계획서가 요구한 **"실측으로 정의한
'현대 지구형 안정 평형' 표준 범위로 행성 상태를 5분류 판정"** 이라는 기능 자체는
그대로 유지되며, 그 판정을 근사 모델이 아니라 정확한 계산으로 수행합니다.

### 참고: 라벨 누수를 겪은 이력

초기 구현에서는 `deltaEnergy`와 `outgoingRadiation`이 입력 피처에 포함되어 있었고,
당시 정확도 0.9996은 성능이 아니라 **라벨 누수의 신호**였습니다. 이 변수들을 빼서
0.9694를 얻었지만, 결국 남은 피처 5개만으로도 라벨이 복원된다는 것을 확인하고
모델 자체를 걷어냈습니다(7장).

이 이력이 남긴 결론은 그대로 유효합니다 — **라벨을 결정하는 값을 입력에 넣으면
모델은 학습하지 않고 정답을 읽는다.**

## 9. 지점 선택 데이터의 한계

행성 만들기의 "특정 지점 선택"은 KIM 실측값을 씁니다(`src/data/climatePoints.js`,
`preset-kim.py` → `build_presets.py`로 생성). 수집한 값 자체는 문헌값과 잘 맞습니다.

| 지점 | 기온 | 구름 | 지표면 알베도 | 문헌 통념값 |
|---|---|---|---|---|
| 서울 | 288.9 K | 55% | 0.107 | — |
| 사하라 | 299.6 K | 21% | **0.323** | 사막 0.30~0.40 |
| 남극 | 230.4 K | 85% | **0.820** | 빙설 0.80~0.90 |
| 태평양 | 300.8 K | 98% | **0.042** | 해양 0.06~0.10 |
| 아마존 | 299.2 K | 87% | **0.144** | 열대림 0.13~0.15 |

지면 상향단파 변수가 없어 알베도는 `1 − Σrss / Σdswrsfc` 로 역산합니다. 일별 비율을
평균하지 않고 합끼리 나누는 이유는, 흐린 날은 분모가 작아 비율이 불안정해지기
때문입니다. `dswrsfc < 50 W/m²` 인 표본은 0/0에 가까워 제외합니다.

이 값은 그 지점의 빙하·바다·육지를 **이미 다 포함한 지표면 전체의 반사율**이므로,
`albedoOf`에서 슬라이더 기반 면적 가중 계산을 대체합니다(구름은 그 위에 그대로 덮습니다).
육지 항에만 넣으면 육지가 없는 지점에서 측정값이 버려집니다 — 남극(육지 0%)의 0.820과
태평양(육지 2%)의 0.042가 무시되고 하드코딩 값이 쓰이게 됩니다.

빙하·바다 슬라이더를 움직이면 실측값은 더 이상 그 행성을 설명하지 못하므로 버려지고,
이후로는 면적 가중 계산으로 돌아갑니다. 실측을 쓸 때만 알베도 하한(0.05)을 0으로
낮춥니다 — 실제 해양은 그보다 어두워(태평양 0.042) 잘리면 반영되지 않습니다.

### ① 계절 표본이 2~8월에 한정됩니다

KIM은 최근 약 180일만 조회할 수 있어 가을·겨울이 통째로 빠집니다. 서울 기준으로
연평균보다 **약 +3.3 °C** 따뜻하게 치우칩니다.

기온·구름은 태양이 필요 없어 조회 구간 전체에 **12일 균등 분산**했지만, 단파복사
(알베도)는 낮이어야 하고 남극이 4월을 넘기면 태양고도가 3° 아래로 떨어져
**2~3월 3일로 따로 고정**했습니다. 지표면 반사율은 계절 변화가 작아(모래·숲·빙설)
이 제약의 손해가 작습니다.

> 두 변수를 같은 날짜로 묶었을 때는 서울 오차가 **−10.0 °C** 였습니다.
> 변수마다 필요한 조건이 달라 날짜를 분리한 것이 이 차이를 만들었습니다.

### ② 지점 ΔE가 평형에서 벗어납니다 — 0차원 모델의 구조적 한계

실측값을 그대로 넣으면 5개 지점 중 4개가 `Energy Deficit`으로 판정됩니다
(사하라 −80.8 / 태평양 −78.0 / 아마존 −66.2, 남극만 +40.1).

실제 지점은 대기순환·해류로 열을 주고받아 **`ASR ≠ OLR` 인 것이 정상**입니다.
사하라는 받은 에너지의 상당량을 고위도로 넘기고, 태평양은 해류로 열을 실어
나릅니다. 그러나 행성 전체를 점 하나로 보는 0차원 모델에는 **그 열수송 항이
없습니다.**

파라미터로 해결되지 않는다는 것을 확인했습니다.

| 시도 | 결과 |
|---|---|
| 위도별 일사 반영(태평양 1.25배, 남극 0.55배) | 개선되지만 **5개 중 0개**만 평형 진입 |
| 지점별 일사를 KIM에서 직접 측정 | 경도별 표본 aliasing으로 값이 어긋남(사하라 49% 오차) |

두 번째가 실패하는 이유는 `hf` 0/6/12/18이 UTC 고정이라 경도마다 다른 현지시각을
찍기 때문입니다(사하라는 낮 표본이 1개, 아마존은 2개). 또한 TOA 일사는 대기가
개입하지 않는 순수 기하량이라 애초에 측정할 대상이 아닙니다.

**게임 진행에는 영향이 없습니다.** 1단계는 `|ΔE| ≤ epsilon`이면 통과하는데, 온도가
평형으로 수렴하면 `OLR ∝ T⁴`이라 ΔE가 저절로 0에 가까워집니다. 아이템은 그 수렴을
가속하는 역할입니다.

| 지점 | 시작 ΔE | 필요 아이템(중앙값) |
|---|---|---|
| 서울 | −10.9 | **0** (시작부터 평형) |
| 남극 | +40.1 | 4~9 |
| 아마존 | −66.2 | 4~7 |
| 태평양 | −78.0 | 5~7 |
| 사하라 | −80.8 | 5~9 |

폭이 넓은 것은 이상기후 이벤트(15~25초마다)가 `advanceTemperature`로 온도를 함께
옮기기 때문입니다. 문제를 오래 붙들수록 이벤트가 더 돌아 아이템이 덜 듭니다.
표의 아래값은 아이템 사이에 이벤트가 5회 도는 경우, 위값은 이벤트를 무시한 경우입니다.

지점마다 고쳐야 할 방향이 뚜렷해 시나리오가 구분됩니다 — 남극만 데우는 방향이고
나머지는 식히는 방향입니다.

> 1차원(위도별) 에너지수지 모델로 확장하면 해결되지만, 물리 코드보다 게임 쪽
> 비용이 큽니다 — 단일 값 물리 결과를 참조하는 곳이 185군데이고, 5분류 판정·온도
> 임계값·아이템·퀴즈·개념 설명이 모두 "행성 전체가 값 하나"라는 전제 위에 있습니다.
> 별도 과제로 남겨 둡니다.

### ③ 지면기압으로 대기 두께를 구분합니다

`ps`(지면기압)가 조회되어 지점별 `atmThickness = ps / 101325` 를 씁니다. 해면기압
(`psl`)은 고도 보정이 들어가 어디서 재도 ≈1.00이라 지점 구분이 되지 않습니다.
남극은 빙상 고도 때문에 **0.665**로, 다른 지점(0.89~1.00)과 뚜렷이 갈립니다.
